# Runner Execution and Container Runtime

This page describes the Rust Runner on `main`. See [CI YAML](ci-yaml.md) for pipeline YAML, job dependencies, and variable rules. The server handles scheduling; the standalone `gity-runner` process claims and runs project jobs.

## Startup and Configuration

At startup, the Runner reads `.env`. Command-line arguments override environment variables with the same name. The project Runner token is generated by the server registration endpoint and passed through `GITY_RUNNER__TOKEN`.

```sh
GITY_RUNNER__TOKEN='project-runner-token' cargo run -p gity-runner -- \
  --server http://localhost:8080 \
  --work-root /srv/gity-runner
```

| Argument | Environment variable | Default and constraints |
| --- | --- | --- |
| `--server` | `GITY_RUNNER__SERVER_URL` | `http://localhost:8080`; HTTP(S), no embedded credentials |
| `--token` | `GITY_RUNNER__TOKEN` | Required; project-specific token |
| `--executor` | `GITY_RUNNER__EXECUTOR` | `container`; `shell` is also supported |
| `--container-bin` | `GITY_RUNNER__CONTAINER_BIN` | `docker`; invokes Docker CLI |
| `--image` | `GITY_RUNNER__IMAGE` | `alpine:3.22`; the job YAML `image` takes precedence |
| `--work-root` | `GITY_RUNNER__WORK_ROOT` | `data/runner`; creates a separate temporary directory for each job |
| `--memory-mb` | `GITY_RUNNER__MEMORY_MB` | 1024 MiB；64–262144 |
| `--cpus` | `GITY_RUNNER__CPUS` | 2；1–256 |
| `--pids-limit` | `GITY_RUNNER__PIDS_LIMIT` | 256；16–65536 |
| `--poll-seconds` | None | 3 seconds; actual wait for an empty queue is limited to 1–60 seconds |
| `--once` | None | Exits after one claim cycle, including when the queue is empty |

The Runner exits before claiming a job if argument parsing or resource-range validation fails. In continuous mode, claim or execution errors produce diagnostics; polling resumes after a 5-second wait.

## Container Execution

Container mode requires the Docker CLI and an accessible Docker daemon. The Runner uses `docker run` to create a job container, mounts the source directory at `/workspace`, mounts the script read-only at `/gity-script.sh`, and runs `sh -eu /gity-script.sh`. The current implementation has no separate Podman, containerd, or Firecracker executor.

On Unix, the job container uses the Runner's UID/GID. The container has memory, CPU, and process-count limits, drops Linux capabilities, and enables `no-new-privileges`. CI variables are passed through a temporary env file with `0600` permissions; each value must be a single line and contain no NUL, carriage return, or newline.

If the Runner itself runs in a container, the host daemon resolves Docker bind-mount source paths. The working directory must appear at the same absolute path in the Runner container and on the Docker host. The optional production Compose `runner` profile uses `GITY_RUNNER_WORK_ROOT` to set the host path, defaulting to `/srv/gity-runner`; this is a Compose variable, while the Runner process still reads `GITY_RUNNER__WORK_ROOT`. Before deployment, ensure UID/GID `10001` can write to that directory and set the supplementary group to match the host Docker socket GID.

The job container receives only job CI variables and the working directory. Access to the Docker socket gives the Runner the ability to manage host containers; keep the Runner process and socket in a trusted environment.

## Shell Execution

`--executor shell` runs scripts directly on the host with `sh -eu` and is suitable only for trusted jobs. The Runner clears the inherited process environment, then sets `PATH`, a temporary job `HOME`, and job variables. Container resource settings do not limit the shell process.

## Source, Logs, and Job Completion

The Runner downloads a ZIP for a fixed commit provided by the server and extracts it into the job working directory. The archive is limited to 256 MiB, and the expanded content to 512 MiB and 100,000 entries. Path traversal, `.git` metadata, and symlinks pointing outside the working directory are rejected.

The Runner sends a heartbeat every 15 seconds and checks the returned job ID and execution count; the old process stops if the job is claimed again. The Runner uploads stdout/stderr in chunks. The server masks project secrets when persisting logs. A Runner uploads at most 4 MiB of output per job and marks excess output as truncated. Only successful jobs upload explicitly declared artifacts; each artifact must be a regular file inside the working directory and no larger than 64 MiB.

On timeout, cancellation, or lease expiration, the Runner terminates the execution process. On Unix it terminates the entire process group; container mode also calls `docker rm --force`. It also reaps child processes and removes the temporary job directory on normal completion. Job status, log, and artifact writes include the execution count from claim time, and the server rejects writes from stale executors.

## Verification

The following Rust tests verify HTTP job claiming by the Runner binary, source download, script execution, logs, artifacts, success and failure reports, timeout, and lease revocation. Container cases require a local Docker daemon and the `alpine:3.22` image.

```sh
cargo test -p gity-runner
cargo test -p gity-runner --test lifecycle docker_binary -- --ignored --nocapture
```

In this workspace, shell and real Docker cases were run on Linux; all 4 execution flow tests passed. Windows process-tree cleanup and other container runtimes were not tested.
