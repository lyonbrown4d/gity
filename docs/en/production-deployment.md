# Deployment Overview

The current Compose deployment entry point is [`deploy/components`](deployment/compose.md); see [image variants](deployment/images.md). This page summarizes the two deployment layouts and their operational boundaries.

Both Compose layouts run on one Docker host. The distributed layout separates processes and data volumes, but it is not a cross-host cluster or automatic failover solution. The current Debian/Alpine role image matrix still needs actual builds and black-box acceptance; local Cargo checks do not substitute for image verification.

## Choose a Deployment Layout

| Layout | Components and data | Exposed entry points | Limitations |
| --- | --- | --- | --- |
| Standalone | One Gity process combines the API, Git, OCI, package, and background modules; the Runner module supervises a separate Runner child process. Uses SQLite and a local object directory by default. Docker-in-Docker (DinD) runs in a separate container. | HTTP `8080`, Git SSH `2222`, OCI `5000` | Compose requires Docker privileged mode; Runner container jobs use a single-host DinD service. |
| Distributed components | API, Git server, Gateway, Registry, Worker, two Git storage nodes, PostgreSQL, SeaweedFS, and a bucket initialization job; Runner and DinD start separately through the `runner` profile. | Gateway HTTP `8080`, SSH `2222`, OCI `5000`; package protocol is forwarded through Gateway to Registry internal port `8082` | Still a single-host Compose deployment. The primary acknowledges Git writes before asynchronous replication; no Raft or automatic failover is provided. |

The distributed Registry serves OCI on `8081` and package HTTP on `8082`. Gateway forwards `/api/v1/projects/{id}/packages` and `/api/v1/repos/{id}/packages` paths to the package service and other main-site HTTP requests to the API. The Git server provides HTTP/SSH collaboration entry points; Git nodes expose only internal storage RPC.

## Distributed Data and Failure Boundaries

In Git cluster configuration, `replicas = 2` means two replicas total: one primary and one remote storage replica. The primary acknowledges a write before asynchronous replication, so acknowledgment does not mean the remote replica has persisted it. Reads select only replicas at the current data generation that have caught up.

Only controlled promotion is supported: the operator specifies a target node, and the system must contact the old primary, place it in a fenced state, verify the target replica, and activate it as the new primary. Promotion fails if the old primary is unreachable. Replica process counts, Compose restarts, and Git mirrors are not lossless automatic failover.

Distributed Compose mounts `git-repositories` and `git-repositories-2` for the two Git nodes and configures separate named volumes for PostgreSQL, SeaweedFS, API, Git server, Worker, Registry, and DinD data. Backups should cover the database, both Git nodes, object storage, and the state of any components that need recovery. Backing up only PostgreSQL is not enough to restore repositories and objects.

## Processes, Credentials, and Identifiers

In standalone, `RunnerModule` starts the Runner as a separate child process; the server handles orchestration and authorization and does not run pipeline scripts directly. A distributed Runner starts only after it is registered to a project; it connects to Gateway using the project-scoped token issued to that Runner. Provide the token only in the process environment when starting the Runner profile; do not write it to documentation, images, or a shared `.env`.

All application containers run as UID/GID `10001`. TLS private keys should be owned by UID/GID `10001` and have `0600` permissions; restrict the deployment certificate directory to `0700`. S3, Angos, and Git-node credential files generated by `prepare-secrets.sh` should be owned by UID/GID `10001` with `0400` permissions, and the directory should be `0700`. Compose mounts only the files each role needs, read-only. Git node certificates must allow both `serverAuth` and `clientAuth`; replicas connect to the source node with their own certificates. The CA signing private key is not mounted into service containers; host root can still read and manage it.

Distributed write processes use distinct Snowflake node IDs: API `1`, Git server `2`, Worker `3`, and Registry package storage `5`. Write processes using the same database must not reuse a node ID. Standalone modules share one generator, configured with node ID `1`.

Roles use the shared `gity-observability` library to emit structured JSON or text logs and can configure Prometheus metrics and OTLP HTTP tracing. Server metrics listen on the container loopback address `127.0.0.1:9090` by default. Runner metrics are disabled by default; when enabled, they default to `127.0.0.1:9091`. Compose does not publish these ports; configure a listener on a trusted container network address for external collection.

Configuration files use the `[observability]` section. OTLP environment variables by role are:

| Role | OTLP collector environment variable |
| --- | --- |
| Standalone, API, Git server, Worker | `GITY_OBSERVABILITY__OTLP_ENDPOINT` |
| Git node | `GITY_GIT_NODE_OBSERVABILITY__OTLP_ENDPOINT` |
| Gateway | `GITY_GATEWAY_OBSERVABILITY__OTLP_ENDPOINT` |
| Registry | `GITY_REGISTRY_OBSERVABILITY__OTLP_ENDPOINT` |
| Runner | `GITY_RUNNER__OBSERVABILITY__OTLP_ENDPOINT` |

## Updates and Recovery

Before an update, create recoverable backups of the database and all related named volumes, and retain the current image tags. Stop services with `down` for the corresponding Compose file; do not add `-v`, or Docker will delete the project’s persistent volumes. After restarting, check Compose health and verify business paths with actual HTTP, Git, package protocol, and OCI operations.

The repository currently contains no record of an executed production backup recovery drill. The backup scope above is an operational requirement derived from current volume mounts; it does not mean end-to-end recovery has been verified. Use actual run records for image matrix results, Git replica failure behavior, and full backup/recovery acceptance.
