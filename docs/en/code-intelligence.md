# Code intelligence

Reading code in the web UI needs five queries: a file outline, a jump to the declaration under the cursor, declarations by name, hover documentation, and declaration-name search. They are answered from a symbol snapshot of the project's default branch, produced by a Runner scan and ingested by the platform.

What ships today is the **lexical layer**: tree-sitter extracts declarations file by file and does not resolve references. "Go to definition" is therefore really "go to the declaration under the cursor" — it can say which `fn` or `struct` a line belongs to, but not which declaration an identifier points at. The precise layer (SCIP) has its shard format and queries implemented in this repository, but is not wired into the platform yet; see "Precise layer (next stage, not shipped)" below.

## Capabilities and limits

| Capability | Endpoint | What the implementation does today |
| --- | --- | --- |
| File outline | `GET /api/v1/projects/{id}/repository/symbols` | Lists every declaration extracted from `path`, ordered by line and column |
| Jump to declaration | `GET /api/v1/projects/{id}/repository/definitions` | Returns the innermost declaration covering the cursor position; `mode` is always `enclosing` |
| Declarations by name | `GET /api/v1/projects/{id}/repository/references` | Declarations whose name matches exactly across the snapshot; not reference sites |
| Hover documentation | `GET /api/v1/projects/{id}/repository/hover` | Name and first documentation line of the declaration under the cursor; `source` is always `lexical` |
| Declaration-name search | `GET /api/v1/projects/{id}/repository/code-search` | Full-text search over declaration names and file paths |

Every response carries `precision` (always `approximate` today) and `index` (whether an index is available, its commit, its indexing time). Both fields are shaped for two coexisting layers, so adding the precise layer changes values but not the response shape.

The limits deserve plain wording:

- **Lexical only.** Declaration positions inside one file are accurate; cross-file name resolution, real definition jumps and reference counting do not exist.
- **Macros are not expanded.** Declarations generated by a macro have no syntax node in the source and cannot be extracted.
- **Overloads and namesakes are not distinguished.** A by-name query returns every declaration with that name, regardless of parameter list, trait implementation or module, so a call site cannot be attributed.
- **Dynamic dispatch, aliases and `use` are not followed.** No name resolver exists; `use` statements are recorded as imports in the archive but take no part in queries.
- **Rust only.** `Language::from_path` recognises `.rs` alone; other files are never extracted.
- **Methods and fields.** Functions inside an `impl` appear as `kind=function` with the impl type as `scope`; fields and local variables are not extracted, and the `method`, `field` and `variable` kinds are currently never produced.
- **Documentation is one line.** The first non-empty line of the `///` or `//!` block goes into `doc`, not the whole block.
- **Innermost means latest line.** Among declarations covering the cursor, `definitions` picks the latest start line; on the same line it prefers a column at or before the cursor, so `Foo::bar` resolves to `bar` rather than `Foo`.

## How the index is produced

Users do not write `.gity-ci.yml` and do not declare a pipeline: the platform enqueues the index job itself after a push.

### The platform enqueues the job

A successful push to the default branch creates one `kind=index` job when the commit is not all zeros and the language statistics include Rust. Fixed fields in that job:

- `tags` is `["gity-indexer"]`, so only a Runner carrying that tag claims it;
- `artifact_name` is `code-index.msgpack.zst`;
- `pipeline_job_name` is `code-index`, which the Runner sees as `CI_JOB_NAME`;
- `trusted_config` is `false`, so repository configuration is never used;
- the maximum attempt count is 2.

System jobs are created through an internal entry point, and the public job-creation endpoint accepts only `noop` and `script`. The index job therefore skips YAML validation and never appears in a pipeline definition; it is visible in the project job list with `kind=index`. Tag pushes, pushes to other branches, and repositories whose language statistics contain no Rust enqueue nothing.

### The Runner scans and uploads

After claiming the job, the Runner executes it in its own process, without a container or an image: it downloads the source ZIP for the pinned commit (256 MiB ceiling), unpacks it with a 100,000-entry and 512 MiB expanded limit, rejecting `.git` metadata, escaping paths and symlinks; it parses every supported file with tree-sitter into a msgpack + zstd archive (`FORMAT_VERSION = 1`); an archive above 64 MiB is an explicit error rather than a truncated upload; finally it uploads the archive as a job artifact.

Lease expiry, cancellation and Runner shutdown all terminate the scan.

### The platform ingests the archive

After the Runner reports success, the platform ingests `kind=index` jobs: it finds the artifact by name, reads the bytes from storage, decompresses and decodes them (an unexpected format version fails), and writes the local index (archive, `current/` and `status.json`).

A failed ingest **does not** rewrite the job status: the job already succeeded, so the failure is only logged and counted in `gity_code_index_ingest_total{result="failure"}`. "Job succeeded" therefore does not mean "index updated"; check that metric and the server log when investigating.

## Prerequisites for an index job

Only a Runner tagged `gity-indexer` can claim an index job. Tags are set when the Runner is registered, are comma-separated, and are matched case-insensitively:

```bash
curl -X POST "$GITY/api/v1/projects/42/runners" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"indexer","tags":"linux,gity-indexer"}'
```

Registration requires a maintainer (role level ≥ 40), and the returned token is shown only once. Without such a Runner the job stays `pending` forever: it does not fail, it does not time out, and no index is produced. The standalone deployment is no exception: the Runner process it starts uses tokens issued by the registration endpoint and carries no tags of its own.

Runners that execute script jobs do not need this tag; conversely, a Runner carrying only `gity-indexer` claims index jobs and nothing else.

## Artifacts and quotas

| Limit | Value | Behaviour when exceeded |
| --- | --- | --- |
| Single source file | 512 KiB | The file is skipped without an error |
| File count | 5000 | Walking stops; the index holds only what was scanned |
| Total source bytes | 64 MiB | Walking stops; same as above |
| Archive artifact | 64 MiB | The Runner fails the job; the server artifact endpoint rejects it too |
| Source ZIP expansion | 100,000 entries / 512 MiB | Extraction fails and the job fails |

Scan quotas are hard-coded in `scan::Limits::default()` and do not read `search.max_files_per_project` or `search.max_file_size_bytes`; those two belong to the text search index.

Reaching a quota sets **no `truncated` marker**: the scan simply stops, and neither the archive, nor `status.json`, nor any response carries a truncation field. The index looks entirely healthy while missing files, so the only way to detect it is to compare `status.json`'s `files` against the real file count. The only explicit errors are the 64 MiB archive ceiling and the server-side artifact limit.

The scan also skips `.git`, `target`, `node_modules`, `vendor`, `dist`, `build`, `.venv`, `__pycache__` and `third_party` directories, plus symlinks, non-UTF-8 files and files that fail to parse.

## Storage layout

```text
data/code-index/                   search.code_index_root
├── 42.lock                        one lock per project: shared for reads, exclusive for writes
└── 42/
    ├── current/                   tantivy index; meta.json marks its presence
    ├── archive/
    │   └── <commit>.msgpack.zst   msgpack + zstd archive; the newest 10 are kept
    └── status.json                commit, files, definitions, archive_bytes, indexed_at
```

`search.code_index_root` defaults to `data/code-index`, can be overridden with `GITY_SEARCH__CODE_INDEX_ROOT`, and must not be empty at startup. The root is created and canonicalised when the service starts; a project path that is a symlink is refused.

Locks and lifecycle match the text search index: `try_lock` from `fs2` on `<root>/<project>.lock`, shared for reads and exclusive for rebuilds, never blocking. The difference shows up when the lock is held: a code-index read fails and surfaces as 500, while the text search index returns an empty result and falls back to scanning Git. A 500 seen during a rebuild is worth a retry.

A rebuild writes the archive, deletes and rebuilds `current/` wholesale, writes `status.json`, and then prunes archives to the 10 newest by modification time. There is no incremental update; `current/` is always new.

Archives are also copied to object storage as `code-index/<project_id>/<commit>.msgpack.zst`, controlled by `search.code_index_remote` (enabled by default). That copy restores a replica whose local snapshot is missing; write and read failures are only logged and counted in `gity_code_index_remote_total`, never affecting the index itself. The query endpoints read the local store only and do not fetch from object storage on a miss.

## HTTP endpoint reference

All five query endpoints are `GET /api/v1/projects/{id}/...` and need project read access: anonymous requests work on public projects, internal projects require a signed-in user, and private projects require project membership.

### Endpoints and parameters

| Endpoint | Parameters | Response fields |
| --- | --- | --- |
| `/repository/symbols` | `path` (required, repository-relative) | `path`, `items[]`, `precision`, `index` |
| `/repository/definitions` | `path`, `line`, `column` (required, 1-based positive integers) | `definitions[]`, `mode`, `precision`, `index` |
| `/repository/references` | `name` (required), `limit` (1–500, default 100) | `references[]`, `total`, `precision`, `index` |
| `/repository/hover` | `path`, `line`, `column` | `hover`, `precision`, `index` |
| `/repository/code-search` | `q` (or `query`, required), `limit` (1–500, default 50) | `matches[]`, `total`, `precision`, `index` |

Elements of `items[]`, `definitions[]` and `matches[]` share one shape: `path`, `name`, `kind`, `scope`, `line`, `line_end`, `column`, `doc`. Elements of `references[]` are `path`, `name`, `line`, `column`, `scope`, without `doc` or `kind`. `index` is `available`, `commit`, `indexed_at`.

A single-file outline returns at most 4096 declarations and a by-name query at most 512, both before `limit` truncates them. `references` reports `total` before `limit` (so at most 512), while `code-search` reports `total` as the number of rows it returned.

### Response envelope and degradation

Successful responses are uniformly `{"code":0,"message":"OK","data":{...}}`. A missing index is not an error: the response has empty arrays, `index.available=false` and `precision="approximate"`, and the HTTP status is still 200.

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "definitions": [],
    "mode": "enclosing",
    "precision": "approximate",
    "index": {"available": false, "commit": "", "indexed_at": ""}
  }
}
```

The same response with an index in place:

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "definitions": [
      {
        "path": "crates/gity-code-intel/src/store.rs",
        "name": "refresh",
        "kind": "function",
        "scope": "Store",
        "line": 77,
        "line_end": 99,
        "column": 3,
        "doc": "Indexes an in-memory archive, replacing the previous snapshot."
      }
    ],
    "mode": "enclosing",
    "precision": "approximate",
    "index": {"available": true, "commit": "5f1c0e2", "indexed_at": "2026-11-02T16:04:11.284Z"}
  }
}
```

`hover.hover` being `null` means no declaration sits at the cursor; when present, `contents_markdown` is the documentation followed by the name, degrades to `` `name` (kind) `` when there is no documentation, and `source` is always `lexical`.

### Error codes

| Status | When it happens |
| --- | --- |
| 400 | `path`, `name` or `q` is missing or empty; `line` or `column` is missing or not a positive integer; `limit` is outside 1–500 |
| 401 | Identity is required but the credentials are absent or invalid, for example an anonymous request on a private project |
| 403 | The identity cannot read the project, or the project token lacks the scope |
| 404 | The project does not exist or was deleted |
| 500 | The index read failed: a rebuild holds the exclusive lock, tantivy errored, or the query string could not be parsed |

The `message` of a 5xx response is replaced with `internal server error`; the concrete reason is only written to the server log.

## Manual refresh

`POST /api/v1/projects/{id}/search/code-index/refresh` rebuilds the index from the default branch HEAD immediately, with no Runner and no need to wait for the next push.

The permission is `RepositoryAdmin`: role level ≥ 40 (maintainer or owner), and super administrators pass as well. **Project tokens cannot call it**, because the operation has no scope that can be granted to a project token and such a request gets 403; use a user token or a session. The request has no body and returns:

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "commit": "5f1c0e2",
    "files": 214,
    "definitions": 3621,
    "indexed_at": "2026-11-02T16:04:11.284Z"
  }
}
```

An empty repository or a missing default branch returns 404 (the upstream errors are `git reference not found` and `git repository is empty`); an index write failure returns 500. When the local rebuild fails, the service tries to restore the same commit's archive from object storage, and only returns the error if that also fails.

## Precise layer (next stage, not shipped)

What follows is a design. The code lives in `crates/gity-scip`, the platform has no caller for it yet, and the endpoints do not return precise results.

### SCIP shard layout

The Runner runs a language indexer (`rust-analyzer scip`, `scip-typescript`, …) and stores `index.scip` zstd-compressed per commit. The server decompresses it, decodes the protobuf (512 MiB ceiling after decompression), and builds a local shard:

```text
<code-intel root>/<project>/scip/
├── manifest.json   commit, indexer, format version, position encoding, counts
├── paths.bin       sorted paths with their occurrence range
├── occ.bin         fixed-size occurrence records, ordered by path and position
├── symbols.bin     repository symbols: kind, documentation and signature offsets
├── external.bin    symbols defined in dependencies
├── texts.bin       source text, when the indexer shipped it
├── docs.bin        documentation and signature text pool
├── refs.bin        CSR: symbol → occurrences
├── coverage.bin    bitset of precisely analysed paths
└── lock            reader/writer lock
```

`FORMAT_VERSION = 2`; version 1 shards are rejected outright and rebuilt from the stored `index.scip`. The manifest is written last and is the commit point; `Shard::open` treats the precise layer as optional and returns `Ok(None)` for every unusable case. Opening maps the eight table files with `memmap2`; one handle holds eight file descriptors, so callers should cache handles rather than reopen per request.

### The three Answer states

| Value | Meaning | Caller behaviour |
| --- | --- | --- |
| `Found` | A definition location was found; for a symbol defined in a dependency `external=true` and the location is the use site | Jump; when `external`, show hover documentation instead |
| `Absent` | The file was precisely analysed, but no symbol sits under the cursor | Return empty without falling back |
| `Uncovered` | The file is outside the precise analysis, or the shard is unusable | Fall back to the lexical layer |

Positions are 1-based lines and columns, with the column unit given by the document's `PositionEncoding`; `Shard::normalized_position` converts a UTF-8 column into the unit that document uses.

### Fallback promise

Once the precise layer is wired in, the response structure stays the same: the lexical layer keeps answering for uncovered files, `precision` moves from `approximate` to a precise value, `hover.source` from `lexical` to `scip`, and `definitions.mode` from `enclosing` to real definition resolution. When a shard is missing, corrupt, truncated, of the wrong format version or locked by a writer, `Shard::open` degrades silently and the request does not fail — which is what lets the precise layer roll out without changing clients.

## Troubleshooting

| Symptom | Cause | What to do |
| --- | --- | --- |
| Endpoints return empty arrays with `index.available=false` | The project has no index yet | Check whether an index job was enqueued; register a Runner tagged `gity-indexer`, or run a manual refresh |
| An index job stays `pending` | No Runner carries the `gity-indexer` tag | Register a Runner or add the tag, and confirm the process is running |
| Only some files appear in the outline | Unsupported language, a file above 512 KiB, a skipped directory, non-UTF-8 content, or the 5000-file / 64 MiB quota | Compare against the quota table; quota truncation has no marker, so compare `files` with the real file count |
| The job fails with `code index archive is N bytes ... limited to 64 MiB` | The archive exceeds the artifact ceiling | Narrow the indexed scope; there is no configuration to raise the ceiling and no truncated upload |
| The job succeeded but the index is still on an old commit | The ingest failed: missing artifact, decode error, unexpected version, unreadable storage | Check `gity_code_index_ingest_total{result="failure"}`, `gity_code_index_enqueue_total` and the server log, then refresh manually |
| A query or refresh returns 500 `internal server error` | A rebuild holds the exclusive lock, or tantivy / IO failed | Retry later; if it persists, check permissions and disk space for `search.code_index_root` |
